Storage credentials and permissions

Storage credentials belong to the messaging engines, not client SDKs or Agent Services. NeonD's credential selection is explicit and independent of endpoint hostname. The default provider is the AWS SDK for Go v2 default credential chain; local deployment templates explicitly select env for RustFS.

AWS default chain​

storage:
  endpoint: s3.us-west-2.amazonaws.com
  bucket: example-neond
  region: us-west-2
  prefix: deployments/example
  tls: true
  credentials:
    provider: default

The engine delegates credential discovery to the AWS SDK: environment credentials, web identity, shared profiles (including configured SSO/credential processes), container credentials and EC2 metadata. Use instance profiles on EC2, a task role on ECS, and Pod Identity or IRSA on EKS. Each deployment needs an appropriately scoped role and its platform-specific trust configuration. The SDK consumes existing identity configuration; NeonD does not create roles or perform interactive login. Operators using profiles must log in first and make the intended AWS profile/cache available to the engine process. A host profile is not automatically inside Docker.

The SDK caches credentials and refreshes expiring role credentials automatically. A failed credential lookup or refresh fails the storage request; it never sends an unsigned request. Storage retries preserve pending data locally until upload succeeds. Monitor backlog during identity-provider outages.

Static environment keys do not refresh automatically. SSO profiles may require a new operator login. Avoid setting static AWS keys alongside workload identity: the chain may select those keys first. Do not set accessKeyEnv, secretKeyEnv, or sessionTokenEnv under default.

RustFS and other S3-compatible stores​

storage:
  endpoint: rustfs:9000
  bucket: neond
  region: us-east-1
  tls: false # Only for an isolated local test network.
  credentials:
    provider: env
    accessKeyEnv: NEOND_STORAGE_ACCESS_KEY
    secretKeyEnv: NEOND_STORAGE_SECRET_KEY
    # sessionTokenEnv: NEOND_STORAGE_SESSION_TOKEN

Deployment supplies the referenced variables to engines using its secret mechanism. No inline secrets are accepted. The env provider reads static values at startup; rotate them with a controlled restart. An expired static session token cannot refresh itself. Config inspection shows reference names, never resolved secret values. The NATS fork retains its earlier iam mode for direct engine users, but NeonD's public configuration offers only default and env.

GCS HMAC credentials fit env, but GCS's XML compatibility semantics have not been qualified. Native GCS ADC/Workload Identity requires a separate backend and is not implemented by this S3 credential mode.

Least-privilege S3 policy​

Provision the bucket separately. Engines do not need bucket creation, bucket-policy administration, ACL management, or account-wide S3 access. For ordinary read/write, recovery and archival with the default block size, scope to one deployment prefix:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::example-neond",
      "Condition": {"StringLike": {"s3:prefix": ["deployments/example/*"]}}
    },
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::example-neond/deployments/example/*"
    }
  ]
}

PutObject covers immutable conditional writes; GetObject covers verification, remote replay and recovery; ListBucket covers prefix-scoped discovery. Region is configured explicitly. Runtime code does not need GetBucketLocation in that path. Do not grant DeleteObject for namespace archival or stream retirement: those retain remote objects. The fork's separately invoked remote garbage-collection execution can delete specifically journaled orphan payloads and needs s3:DeleteObject on the same object prefix if an operator enables that operation. It is not required to complete normal NeonD archival. Integration-test cleanup may need more permissions than production engines; do not copy a test administrator's policy into production.

For large objects where the S3 library chooses multipart upload, permit s3:AbortMultipartUpload on that object prefix for failed-upload cleanup. Multipart creation/upload/completion use s3:PutObject; do not add multipart-list permissions unless the actual deployed client path needs them. Bucket lifecycle cleanup for abandoned multipart uploads is a separate operator setting. SSE-KMS deployments also need key-policy/IAM permissions such as kms:GenerateDataKey and kms:Decrypt for the selected key; those are not needed for ordinary S3-managed encryption. This policy targets general-purpose buckets, not S3 Express directory buckets.

Diagnostics and qualification​

Monitor upload/fetch errors, retries, backlog, archive failures, and sanitized credential-error logs. Keep local data intact while correcting credentials. Configuration inspection shows credential references, not resolved secrets.

Local tests cover credential discovery, refresh, expiry, provider outages and recovery against RustFS. They do not qualify every AWS identity configuration or GCS compatibility. AWS role-expiry qualification is tracked in NeonD #9.
